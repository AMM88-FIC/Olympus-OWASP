# Layer 3 Evidence Schema — Full Specification

Version: 1.2.3
Status: Implemented
Last updated: 2026-05-01

This document is the authoritative reference for the Layer 3 evidence
schema. It describes every file, every model, every field, and every
allowed value. The implementation lives in `app/evidence/models.py`.

---

## Design principles

1. Every file carries `schema_version: "1.2"` and a metadata header.
2. Every evidence record has a globally unique `id` (domain-prefixed),
   a `source` pointing back to the original artifact, and a
   `record_hash` for content-based identity.
3. Every code-derived record carries `snippet_context`, `taint_sources`,
   `noise_signals`, and `reachable_from`.
4. Cross-file relationships are expressed via `related_ids` (populated
   in a second pass after all builders run).
5. Taint analysis is intra-procedural only. Every `TaintSource` carries
   `intraprocedural_only: true`.
6. Storage format is JSON. Prompt-time serialization (YAML, compact
   line format) happens at the Layer 4 boundary.
7. App context is captured as **behavioral capability flags** in
   `app_capabilities.json`, derived from manifest declarations and code
   patterns. The extractor never infers a category label; it records
   facts about what the app is structurally capable of doing.
8. `_validation_errors.json` records every silent failure so Layer 4
   can distinguish "nothing found" from "extraction failed".

## Common substructures

These types are used across multiple evidence files.

### Source

Points back to the exact artifact location that produced a record.

```
Source
  artifact        "manifest" | "java" | "smali" | "nsc_xml" |
                  "resource" | "asset" | "dex" | "native_lib"
  path            str                    relative path to the file
  line_start      int | None             1-indexed start line (code only)
  line_end        int | None             1-indexed end line (code only)
  xpath           str | None             XPath expression (XML only)
  dex_string_id   int | None             position in sorted string list
  extractor       str                    extractor name + version
  tool            str                    tool name + version
```

### SnippetContext

Surrounding lines for any code-derived record.

```
SnippetContext
  before          list[str]              lines before the call site
  after           list[str]              lines after the call site
  window_lines    int = 5                configured window size
```

### TaintSource

Intra-procedural taint origin detected near a call site.

```
TaintSource
  source_type     "intent_extra" | "intent_data" | "uri_parse" |
                  "broadcast_receive" | "provider_query" |
                  "webview_input" | "network_input" | "clipboard" |
                  "file_read" | "user_input" | "unknown"
  expression      str                    matched expression text
  parameter_position  int               0-indexed parameter position
  intraprocedural_only  bool = True      always True in v1.2
  confidence      float [0.0, 1.0]
```

### NoiseSignal

Flags a record as likely low-relevance for deprioritization.

```
NoiseSignal
  signal          "in_test_code" | "in_debug_only_class" |
                  "in_third_party_sdk" | "in_generated_code" |
                  "in_kotlin_stdlib" | "in_play_services"
  confidence      float [0.0, 1.0]
  notes           str | None
```

### GeneratedBy

Identifies the extractor and tool that produced a file.

```
GeneratedBy
  extractor       str                    e.g. "manifest_parser_v1"
  tool            str                    e.g. "apktool-2.12.1"
```

## Base record types

### EvidenceFile (base for every top-level file)

```
EvidenceFile
  schema_version  str = "1.2"
  job_id          str
  generated_at    str                    ISO-8601 UTC timestamp
  generated_by    GeneratedBy
```

### BaseRecord (base for every evidence record)

```
BaseRecord
  id              str                    domain-prefixed unique ID
                                         (e.g. "cmp-001", "api-042")
  confidence      float [0.0, 1.0]
  related_ids     list[str]              IDs of related records in
                                         any evidence file
  source          Source
  record_hash     str                    SHA-256 of canonical fields;
                                         content-based identity
```

### CodeRecord (base for records derived from Java/smali)

Inherits all BaseRecord fields, plus:

```
CodeRecord
  caller_class    str                    fully qualified class name
  caller_method   str                    method name
  snippet         str                    the matched line(s)
  snippet_context SnippetContext
  taint_sources   list[TaintSource]      empty when none detected
  reachable_from  list[str]             component IDs that can reach
                                         this call; empty until
                                         reachability analysis runs
  extraction_track  "readable" | "bytecode"
  noise_signals   list[NoiseSignal]      empty when none detected
```

### 1. app_metadata.json

Base context included with every MASVS evaluation. One record per job.

**File model**

```
AppMetadataFile (EvidenceFile)
  app                 AppInfo
  dex_files           list[DexFile]
  native_libraries    list[NativeLibrary]
  certificates        list[Certificate]
  certificates_status "extracted" | "none_found" |
                      "extraction_failed" | "unavailable"
  signing_schemes     SigningSchemes              (added v1.2.3)
  app_context         AppContext
  extraction_track    "readable" | "bytecode"
  source              Source
```

**AppInfo**

```
  package_name    str
  version_name    str | None
  version_code    str | None
  min_sdk         int | None
  target_sdk      int | None
  compile_sdk     int | None
  apk_sha256      str
  apk_size_bytes  int | None
```

**DexFile**

```
  path            str
  size_bytes      int
  class_count     int
```

**NativeLibrary**

```
  name            str
  abis            list[str]
  path            str
  size_bytes      int | None
  sha256          str | None
```

**Certificate**

Cryptographic identity of an APK signer. The fields beyond
`issuer`/`subject` were added in v1.2.3 to enable verdicts on
signing-related MASTG tests (TEST-0046, TEST-0048, TEST-0054 family).

```
  issuer              str                   subject DN of the issuing CA
                                            (typically self-signed for
                                            developer certificates)
  subject             str                   subject DN of the signer
  not_valid_before    str | None            ISO-8601 timestamp
  not_valid_after     str | None            ISO-8601 timestamp
  hash_algo           str | None            e.g. "sha256"
  signature_algo      str | None            e.g. "sha256"
  serial_number       str | None            uppercase hex
                                            (added v1.2.3)
  public_key_algorithm str | None           "rsa" | "ec" | "dsa"
                                            (added v1.2.3)
  public_key_bits     int | None            e.g. 2048
                                            (added v1.2.3)
  sha1_fingerprint    str | None            uppercase hex with colons
                                            (added v1.2.3)
  sha256_fingerprint  str | None            uppercase hex with colons
                                            (was always nullable, now populated)
  md5_fingerprint     str | None            uppercase hex with colons
                                            (added v1.2.3)
  pem                 str | None            PEM-encoded certificate for
                                            downstream verification
                                            (added v1.2.3)
  is_debug_cert       bool = False          heuristic match against the
                                            Android debug keystore DN
  is_self_signed      bool | None           heuristic: issuer == subject
                                            (added v1.2.3)
  is_expired          bool | None           computed against UTC now
                                            (added v1.2.3)
```

**SigningSchemes** (added v1.2.3)

APK signing scheme presence flags. An APK can be signed with multiple
schemes simultaneously. v1-only signing is vulnerable to the Janus
attack (CVE-2017-13156) and is explicitly checked by MASTG-TEST-0046.

```
  v1              bool                JAR signing (META-INF/*.RSA|*.DSA)
  v2              bool                APK Signature Scheme v2 (Android 7.0+)
  v3              bool                APK Signature Scheme v3 with rotation
                                      support (Android 9+)
  v4              bool                APK Signature Scheme v4 incremental
                                      signing (Android 11+)
  v1_only         bool                convenience flag — true iff v1 is
                                      present and v2/v3/v4 are all absent.
                                      Verdict prompts checking for the
                                      Janus vulnerability read this directly.
```

**AppContext** (deprecated in v1.2.1 — retained for backward compatibility)

```
  category        "browser" | "vpn" | "password_manager" |
                  "banking" | "health" | "developer_tool" |
                  "messaging" | "social" | "ecommerce" |
                  "media" | "productivity" | "game" |
                  "generic" | "unknown"
                  Default: "unknown"
  category_source "user_provided" | "inferred_from_package" |
                  "default"
                  Default: "default"
  interpretation_notes  list[str]
```

The `app_context` field is retained on `AppMetadataFile` for schema
stability but is deprecated as of v1.2.1. New verdict prompts should
read behavioral capability flags from `app_capabilities.json` instead
of relying on a category label. The original v1.2 design required
human-provided category at job creation, which broke the automation
goal of the pipeline. Behavioral flags derived from manifest
declarations and code patterns produce more reliable, automation-
friendly context. A future v1.3 will remove this field entirely.

### 13. strings.json

Filtered string constants from DEX bytecode, grouped by category.

**File model**

```
StringsFile (EvidenceFile)
  records         list[StringRecord]
```

**StringRecord** (extends BaseRecord, prefix: `str`)

```
  category        "url" | "file_path" | "suspicious_keyword" |
                  "possible_secret" | "ip_address" | "email" |
                  "jdbc_string" | "ipc_action" | "content_uri"
  value           str
  is_cleartext    bool | None          True for http:// URLs
  entropy_bits    float | None         Shannon entropy; possible_secret only
  referenced_in   list[StringCaller]   back-references to call sites
```

**StringCaller**

```
  caller_class    str
  caller_method   str
  source          Source
```

**Category rules**

```
url               Matches http://, https://, ftp://, jdbc:
file_path         Starts with /data/, /sdcard/, /storage/, /proc/
ip_address        Matches IPv4 address pattern
email             Matches email address pattern
jdbc_string       Starts with jdbc:
content_uri       Starts with content://
ipc_action        Matches com.example.ACTION_NAME pattern
suspicious_keyword  Contains: password, passwd, secret, token,
                    api_key, apikey, authorization, bearer,
                    credential, private_key, access_key, auth_token,
                    client_secret
possible_secret   Length > 40, ASCII, high Shannon entropy (≥ 3.5 bits),
                  no match to other category
```

### 20. app_capabilities.json

Behavioral capability flags derived from other Layer 3 evidence. The
builder runs after all primary builders and produces facts about what
the app is structurally capable of doing — never inferred categories
or labels. Verdict-time prompts read these flags as evidence to
calibrate test outcomes.

The set of capability keys is fixed by the builder. Adding a new
capability requires updating both the builder and any test instructions
that consume it.

**File model**

```
AppCapabilitiesFile (EvidenceFile)
  capabilities    dict[str, CapabilityFlag]
```

**CapabilityFlag**

```
  detected        bool                  whether the capability is present
  confidence      float [0.0, 1.0]      reliability of the detection
                                        1.0 — OS-enforced contracts
                                        0.6 to 0.95 — behavioral signals
                                        0.0 — evidence to detect was unavailable
  evidence_ids    list[str]             cross-references to source records
  rationale       str | None            brief why-this-was-detected note
  record_hash     str                   content-based identity
```

**Capability keys produced by the builder (v1.2.1)**

OS-contracted services (confidence 1.0 when both intent action and
gate permission are present):

```
implements_vpn_service              VpnService + BIND_VPN_SERVICE
implements_autofill_service         AutofillService + BIND_AUTOFILL_SERVICE
uses_accessibility_service          AccessibilityService + BIND_ACCESSIBILITY_SERVICE
implements_input_method_service     InputMethod + BIND_INPUT_METHOD
implements_device_admin             DEVICE_ADMIN_ENABLED + BIND_DEVICE_ADMIN
implements_notification_listener    NotificationListenerService +
                                    BIND_NOTIFICATION_LISTENER_SERVICE
```

Manifest-derived (confidence 1.0 for declarations):

```
declares_browsable_https_links      browsable HTTPS deep links present
has_file_provider                   FileProvider component declared
```

Behavioral / code-derived (confidence bounded by detection method):

```
loads_url_from_user_input           taint-traced URL flow into WebView.loadUrl
                                    (capped at 0.75; intra-procedural)
writes_to_downloads_directory       DownloadManager.enqueue (0.92) or
                                    file_external write to Downloads path (0.75)
reads_from_external_storage         external storage permission AND/OR
                                    file_external storage record (up to 0.95)
```

**Confidence interpretation**

- `confidence == 1.0` — OS-enforced. Cannot be present without OS recognizing the capability.
- `confidence 0.85 to 0.99` — strong static signal; minimal uncertainty.
- `confidence 0.7 to 0.84` — pattern-matched or heuristic; low false-positive risk but possible false negatives.
- `confidence < 0.7` — partial signal; should not drive a verdict alone.
- `confidence == 0.0` — required upstream evidence was unavailable; capability is unknown rather than confirmed absent.

**Detection unavailability**

When an upstream evidence file required for a capability is missing
(because that builder failed), the capability is recorded as
`detected: false, confidence: 0.0` with a rationale like
`"Cannot determine: components evidence unavailable"`. This is
distinguishable from a confirmed absence (`detected: false, confidence
>= 0.85`) and verdict prompts must treat the two cases differently.

### 21. native_binaries.json (added v1.2.2)

Cheap-to-extract content of every native library bundled in the APK.
Captures ELF security flags, imported and exported symbols (curated
into security-relevant categories), needed libraries, and filtered
string constants from `.rodata`.

The goal is that for most native-related verdicts, the LLM can reach
a conclusion from L1 alone — same role `crypto_usage.json` plays for
Java crypto. L3 native (Ghidra decompilation) becomes a rare
verification path used only when L1 plus L2 (the Java caller) are
insufficient.

The builder runs in the same phase as `native_methods.json`. The two
files are complementary: `native_methods` captures the Java-side JNI
declarations, `native_binaries` captures the binary-side content.
Neither depends on the other.

v1.2.2 emits **one record per .so file**, with no content-hash
deduplication. APKs that ship the same logical library compiled for
multiple ABIs produce N records (one per ABI directory). The `paths`
and `abis` fields on each record are single-element lists for
forward-compatibility with v1.3, where these fields will contain the
deduplicated multi-location lists.

This deliberate redundancy is documented in the v1.3 roadmap section
at the end of this spec. The trade-off favors schema simplicity now
(every `Source.path` is a real file path, no sentinels or special
cases) at the cost of file size for native-heavy multi-ABI APKs.

**File model**

```
NativeBinariesFile (EvidenceFile)
  records             list[NativeBinaryRecord]
  total_libraries     int                 total .so files found in lib/
  total_records       int                 same as len(records); v1.2.2 emits
                                          one record per file, so this equals
                                          total_libraries. Will diverge in v1.3
                                          when content-hash dedup returns.
  total_strings       int                 string records across all libraries
```

**NativeBinaryRecord** (extends BaseRecord, prefix: `nlib`)

```
  name                str             e.g. "libfoo.so"
  paths               list[str]       paths this binary appears at.
                                      v1.2.2: always single-element
                                      (one record per file). v1.3: will
                                      contain all paths after dedup.
                                      e.g. ["lib/arm64-v8a/libfoo.so"]
  abis                list[str]       ABIs this binary serves.
                                      v1.2.2: always single-element.
                                      v1.3: will contain all matching ABIs.
  size_bytes          int
  sha256              str             content hash. In v1.2.2 may repeat
                                      across records (same content under
                                      multiple ABIs). v1.3: unique per record.
  elf_class           "ELF32" | "ELF64"
  machine             "AArch64" | "ARM" | "x86" | "x86_64" |
                      "MIPS" | "RISC-V" | "unknown"
  stripped            bool            symbol table absent
  security_features   SecurityFeatures
  imports             NativeImports
  exports             NativeExports
  needed_libraries    list[str]       DT_NEEDED entries
  strings             list[NativeStringRecord]
  suspicious_patterns list[str]       pre-computed cross-checks
```

**SecurityFeatures**

Directly answers MASTG-TEST-0044. All flags extracted from `readelf`
without any disassembly.

```
  pie                 bool            Position Independent Executable
                                      (DT_FLAGS_1 PIE bit or ET_DYN type)
  nx                  bool            non-executable stack
                                      (PT_GNU_STACK without PF_X)
  relro               "none" | "partial" | "full"
                                      partial: PT_GNU_RELRO present
                                      full: PT_GNU_RELRO + DT_BIND_NOW
  stack_canary        bool            __stack_chk_fail or __stack_chk_guard
                                      in dynamic symbols
  fortify_source      bool            *_chk symbols imported (e.g. __memcpy_chk)
  symbols_stripped    bool            no .symtab section present
```

**NativeImports**

Curated categorization of imported symbols. The categories below are
fixed; symbols that match none are aggregated in `total_count` but not
listed individually.

```
  total_count         int                 every distinct imported symbol
  by_category         dict[str, list[str]]
                          keys (always present, may be empty list):
                          - "crypto":           AES_*, EVP_*, SHA*, RSA_*,
                                                BN_*, CRYPTO_*, MD5_*, HMAC_*
                          - "tls":              SSL_*, TLS_*, X509_*, BIO_*
                          - "network":          socket, connect, send, recv,
                                                getaddrinfo, gethostbyname
                          - "process":          fork, execve, prctl, kill,
                                                getpid, getppid
                          - "file_io":          open, openat, read, write,
                                                fopen, fwrite, fread, stat
                          - "dynamic":          dlopen, dlsym, dlclose,
                                                dlerror, dl_iterate_phdr
                          - "debug_detection":  ptrace, getauxval,
                                                __system_property_get
                          - "root_detection":   string-based; populated when
                                                imports + .rodata strings
                                                jointly suggest root checks
                          - "jni":              JNI_OnLoad, RegisterNatives,
                                                JNIEnv_*, GetEnv
  interesting_imports list[InterestingImport]
                          actual symbol names that drove categorization
```

**InterestingImport**

```
  name                str                 e.g. "AES_encrypt", "ptrace"
  category            str                 one of the keys above
  source_library      str | None          DT_NEEDED hint when available
                                          (e.g. "libssl.so" for SSL_* symbols)
```

**NativeExports**

```
  total_count         int                 every distinct exported symbol
  jni_entry_points    list[JniEntryPoint]
  registered_natives  bool                RegisterNatives present in imports
                                          (suggests dynamically-bound natives
                                          that don't follow Java_* naming)
```

**JniEntryPoint**

Cross-references with `native_methods.json` records.

```
  symbol              str                 e.g. "Java_com_example_Crypto_encrypt"
  java_class          str                 decoded from symbol
  java_method         str                 decoded from symbol
  related_native_method_id  str | None    ID from native_methods.json when
                                          the Java declaration is found
```

**NativeStringRecord** (extends BaseRecord, prefix: `nstr`)

Strings extracted from `.rodata` and `.data` sections, filtered to keep
only those matching a category. Uncategorized strings (C runtime
noise, format specifiers, etc.) are dropped to keep the file small.

The category enum and detection rules mirror `strings.json` so verdict
prompts can apply the same reasoning to native and DEX strings. The
two categories specific to native are `jni_signature` and `section`.

```
  category            "url" | "cleartext_url" | "file_path" |
                      "suspicious_keyword" | "possible_secret" |
                      "ip_address" | "email" | "jdbc_string" |
                      "ipc_action" | "content_uri" |
                      "jni_signature" |
                      "hardcoded_api_key" | "hardcoded_password" |
                      "bearer_token" | "certificate_pin" |
                      "high_entropy_unknown"
  value               str
  is_cleartext        bool | None
  entropy_bits        float | None
  offset              int                 byte offset in the .so file
  section             "rodata" | "data" | "unknown"
  secret_detection_reason  str | None
  false_positive_likelihood  "low" | "medium" | "high" | None
```

**Suspicious patterns**

Pre-computed cross-checks that combine signals from imports, strings,
and other fields into a single citable finding. Same role
`obfuscation.signals` plays for DEX-derived obfuscation.

```
suspicious_patterns     list[str]
```

Detection rules (each emits a string when triggered):

```
"native_anti_debug"
    ptrace OR prctl(PR_SET_DUMPABLE) imported AND
    .rodata contains anti-debug strings ("/proc/self/status",
    "TracerPid", etc.)

"native_root_detection"
    file_io imports AND .rodata contains root paths
    ("/system/bin/su", "/system/xbin/su", "/sbin/su",
    "Superuser.apk", "magisk")

"native_dynamic_loading"
    dlopen imported AND .rodata contains "lib*.so" string references

"native_crypto_present"
    >= 3 distinct crypto-category imports

"native_tls_present"
    SSL_CTX_set_verify imported OR (>= 3 distinct tls-category imports)

"native_url_in_rodata"
    .rodata contains a string matching the cleartext_url or url category

"native_high_entropy_secret"
    .rodata contains a string with category="high_entropy_unknown"
    and length >= 32

"native_dynamic_jni_registration"
    RegisterNatives imported (suggests JNI methods that won't appear
    in the export table under Java_* naming)
```

Each pattern is a bare string — the LLM's rationale cites the pattern
name and explains why it matters in context. Detailed evidence
(specific imports, specific strings) lives in the parent record's
`imports` and `strings` fields.

**Performance bound**

For a typical app with 4 ABIs and 5 distinct libraries (20 binaries
before deduplication, often 5-10 after):

```
strings -a -n 6              1-3s per binary
readelf parsing              <1s per binary (via python-elftools)
nm -D                        <1s per binary
categorization + filtering   <500ms per binary
```

Roughly 60-80 seconds added for a native-heavy app; near zero for
apps with no native libraries. Acceptable.

**Cross-references**

The `cross_references.resolve_all()` post-processing pass populates:

- `JniEntryPoint.related_native_method_id` → `native_methods.json#jni-N`
  by matching `expected_jni_symbol`
- `NativeBinaryRecord.related_ids` → `app_metadata.native_libraries`
  records that share the same binary path
- `NativeStringRecord.related_ids` → other string records (DEX or
  native) with the same value, useful for finding the same key
  hardcoded across both

**Required tools**

The builder requires these on the analysis host:

- `binutils` package for `nm`, `readelf`, `strings`, `objdump`
- `python-elftools` for stable ELF parsing (preferred over scraping
  `readelf` output)

If the tools are missing, the builder records a `_validation_errors.json`
entry and emits an empty `NativeBinariesFile` with `total_libraries: 0`
rather than crashing the pipeline.

### 22. sensitivity_signals.json (added v1.2.3)

Pre-computed signals indicating which records elsewhere in the
evidence likely involve sensitive data. The builder walks code-bearing
records (`storage_usage`, `api_usages`, `network_usage`, `crypto_usage`,
`strings`, `outgoing_intents`) and emits one or more
`SensitivitySignalRecord` entries when a name or value matches the
curated catalog of sensitivity patterns.

The goal is to give verdict prompts a concrete, citable answer to
"does this evidence handle sensitive data?" rather than asking the LLM
to judge sensitivity itself. A storage_usage record with a matching
sensitivity signal is far more justifiable as a `fail` than the same
record without one.

Signals are split into two categories with deliberately different
semantics:

- **credential** — tokens, keys, passwords, secrets. Sensitivity is
  intrinsic to the data type. Storage in shared locations or
  transmission over cleartext is a fail regardless of consent.
- **pii** — emails, phone numbers, identity documents, location data.
  Sensitivity is context-dependent. Storage is acceptable; specific
  uses (logging, sending to third parties) are problematic.

The two categories drive verdicts differently and should be tracked
separately. MASTG-STORAGE / NETWORK tests primarily care about
credentials; MASTG-PRIVACY tests care about PII.

**File model**

```
SensitivitySignalsFile (EvidenceFile)
  records                     list[SensitivitySignalRecord]
  credential_signal_count     int       count of category=credential
  pii_signal_count            int       count of category=pii
  proprietary_signal_count    int       count where in_proprietary_code=True
  third_party_signal_count    int       count where in_proprietary_code=False
```

**SensitivitySignalRecord** (extends BaseRecord, prefix: `sens`)

```
  cited_evidence_id   str                   the record this signal annotates
                                            (e.g. "stor-042", "api-117")
  category            "credential" | "pii"
  signal_type         str                   hierarchical name describing
                                            the detection rule that fired
                                            (see "Signal type taxonomy" below)
  signal_strength     "high" | "medium" | "low"
                                            calibrated by the catalog and
                                            adjusted for code provenance
  matched_token       str                   what specifically matched
                                            (variable name, regex match,
                                            API method)
  rationale           str                   human-readable explanation
                                            verdict prompts can quote
  in_proprietary_code bool                  False when the originating
                                            record has noise_signals
                                            indicating third-party code,
                                            test code, or generated code
```

**Signal type taxonomy**

The `signal_type` field uses a hierarchical naming scheme so verdict
prompts can match prefixes rather than enumerating individual names:

```
credential_pattern:google_api_key       structural regex match
credential_pattern:jwt_token            JWT structure detected
credential_pattern:bearer_token         Bearer auth header format
credential_pattern:private_key_block    PEM private key marker
credential_pattern:url_with_embedded_credentials
                                        password embedded in URL
credential_pattern:<service>            other curated service patterns

credential_keyword:direct_name          target name matches credential keyword
                                        (e.g. SharedPreferences key "auth_token")
credential_keyword:string_literal       string passed to API matches keyword
                                        (e.g. getString("password"))
credential_keyword:identifier           variable name matches keyword
                                        (downgraded one strength level —
                                        more false positives expected)

sensitive_api_call:keystore_access      KeyStore API used
sensitive_api_call:account_manager      AccountManager API used
sensitive_api_call:android_keystore     android.security.keystore used
sensitive_api_call:secret_key_handling  javax.crypto.SecretKey used

pii_pattern:us_ssn                      SSN format match
pii_pattern:credit_card_number          Luhn-validated card number
pii_pattern:email_address               email regex match
pii_pattern:phone_e164 / phone_general  phone number formats
pii_pattern:gps_coordinate_pair         lat/lng pair

pii_keyword:direct_name                 etc., as for credential_keyword
pii_keyword:string_literal
pii_keyword:identifier

sensitive_api_call:location_manager     LocationManager API used
sensitive_api_call:fused_location       FusedLocationProviderClient used
sensitive_api_call:contacts_provider    ContactsContract query
sensitive_api_call:biometric_prompt     BiometricPrompt API used
sensitive_api_call:telephony_manager    TelephonyManager (IMEI, phone#)
sensitive_api_call:android_id_read      Settings.Secure.ANDROID_ID
sensitive_api_call:sms_provider         SMS content provider
sensitive_api_call:call_log_provider    CallLog content provider
sensitive_api_call:calendar_provider    CalendarContract query
sensitive_api_call:fingerprint_api      legacy fingerprint API
```

**Strength calibration**

```
high    structural match leaves no reasonable doubt:
        - Google API key regex, JWT, Bearer token, private key block
        - SSN format, Luhn-valid credit card
        - HIGH-tier credential keywords matching a target name or
          string literal (password, auth_token, secret_key, etc.)
        - Sensitive API calls to credential-handling APIs
medium  strong signal but plausible false positives exist:
        - MEDIUM-tier credential keywords (token, secret, credential
          alone)
        - PII keywords matching target names or string literals
        - Credit card candidates (before Luhn validation)
        - Sensitive API calls to context-dependent APIs
low     heuristic match useful only in combination with other signals:
        - LOW-tier keywords matched against split parts only
          (key, salt, hash, name, age, country)
        - Identifier-source matches (variable names in code) that have
          been downgraded one level from their catalog strength
        - Email and phone matches in unknown context
```

**Provenance filter**

The `in_proprietary_code` field is set to `False` when the originating
record's `noise_signals` contains any of:

```
in_third_party_sdk
in_test_code
in_generated_code
```

These signals are still emitted (so verdict prompts can see them),
but flagged so prompts can downweight them. The reasoning: a
credential keyword inside a third-party SDK is typically not
actionable for the developer, but credential data flowing from
proprietary code into a third-party SDK call IS the developer's
responsibility — and that case is captured because the originating
record (the proprietary code calling the SDK) is not flagged as
third-party.

**Catalog scope**

Catalog v1 ships in `_sensitivity_patterns.py` with:

- 18 credential structural patterns covering major API key formats
  (Google, AWS, Stripe, GitHub, Slack, SendGrid, Mailgun, npm),
  JWT/Bearer/Basic auth, PEM private keys, and URLs with embedded
  credentials
- 7 PII structural patterns (SSN, credit card with Luhn, email,
  phone E.164 and general, IPv4, GPS coordinates)
- 25 high-strength credential keywords, 17 medium, 5 low
- 9 high-strength PII keywords, 16 medium, 8 low
- 14 sensitive Android API patterns (KeyStore, AccountManager,
  LocationManager, ContactsContract, BiometricPrompt, etc.)

The catalog is intentionally curated rather than comprehensive. Lists
like TruffleHog's regex set cover thousands of services; this catalog
covers the common cases that produce most of the value at near-zero
false positive rate. New patterns can be added without code changes
elsewhere.

**Cross-references**

The `cited_evidence_id` field links each signal back to the record it
annotates. Verdict prompts that need signals for a specific record
filter on this field. The `related_ids` field on `BaseRecord` carries
the same link in the standard cross-reference format.

## Static analysis limitations (always present in coverage.json)

These are emitted unconditionally for every job:

- Server-side logic cannot be verified from APK alone.
- Runtime certificate pinning behavior requires dynamic testing.
- Taint tracking does not follow variables across method boundaries.
- Native library internals (.so files) are not decompiled.
- Dynamically registered JNI methods (RegisterNatives) may bind to
  symbols invisible to static analysis.
- Runtime behavior of resilience controls (root detection,
  anti-debugging) requires dynamic testing to verify effectiveness.

## Explicitly deferred to v2

The following features are not in v1.2 and are documented here to
prevent re-proposals without reading this history.

- **Reachability analysis / call graph**: requires Androguard call graph
  traversal. The `reachable_from` field exists as a placeholder.
- **Interprocedural taint analysis**: requires FlowDroid or similar.
  Out of scope for static extraction.
- **Native code decompilation (Ghidra-tier)**: full disassembly and
  decompilation of `.so` function bodies is L3 territory and remains
  out of scope for the automatic pipeline. v1.2.2 added ELF metadata,
  symbol categorization, and string extraction in `native_binaries.json`,
  but does not decompile instructions. When the LLM needs bytecode-level
  semantics for a native function, it consults Ghidra output as L3
  evidence on demand.
- **`auth_decisions.json`**: modeling auth decisions statically is
  unreliable. LLM reads source instead.
- **Removal of `app_metadata.app_context`**: deprecated in v1.2.1,
  retained for schema stability. v1.3 will remove this field entirely.
  All app-context reasoning has moved to `app_capabilities.json`.
- **CVE database lookups** for third-party SDK vulnerabilities:
  requires external data source integration.
- **Prompt-time serialization** (YAML / compact line format): a prompt
  assembler concern, not a Layer 3 concern.

## Planned for v1.3

Changes scoped for the next minor revision. These are committed
direction, not aspirational — when v1.3 ships, every item below will
land together as a single coherent migration.

### Multi-location source representation

**Problem in v1.2.2.** The `Source` model assumes one record corresponds
to one source location. Several real cases break this assumption:

- The same `.so` content appears at multiple paths in `lib/<abi>/`
- A permission is declared multiple times in the manifest with different
  attributes (each declaration has its own xpath)
- A string constant appears in several Java files at different line ranges
- A class is compiled into multiple DEX files

v1.2.2 sidesteps the first case by emitting one record per file (no
deduplication), accepting redundancy. The other cases are not yet
common enough to require addressing, but the schema cannot model them
cleanly when they do arise.

**Why a `list[str]` in `Source.path` is wrong.** A first instinct is to
make `Source.path` a list of strings. That implicitly claims every
other field of `Source` (`xpath`, `line_start`, `line_end`,
`dex_string_id`) applies uniformly across all paths in the list. That
is only true for the native binary case where content is identical
across paths. For permissions declared multiple times, each declaration
has its own xpath. For strings appearing in multiple files, each
occurrence has its own line range. A path-only list forces a fiction
that breaks the moment a record's other fields differ per location.

**v1.3 change.** `BaseRecord.source` becomes `list[Source]`. Each
location is described by a complete `Source` object with its own path,
xpath, line range, and DEX ID. Single-location records carry a
one-element list. Multi-location records carry one Source per
location.

```
BaseRecord
  id              str
  confidence      float
  related_ids     list[str]
  source          list[Source]            one or more locations; never empty
  record_hash     str
```

The system prompt gains one rule: "`source` is a list of locations.
The first element is canonical for single-source records; iterate over
the list for multi-source records when relevant." That rule is uniform
across all record types — no per-record-type exceptions, no sentinels,
no path-list-versus-Source-list ambiguity.

Single-location records (the vast majority) read `record.source[0].path`
in code, no different in practice from `record.source.path` today.
Multi-location records read `[s.path for s in record.source]` or iterate
to access per-location xpaths, lines, etc.

### Reintroduction of native binary deduplication

With multi-location sources in place, `native_binaries.py` returns to
its v1.2.2 design intent: emit one record per distinct binary content
(by sha256), with `source` listing every `Source` object — one per
location. Records become unambiguously content-keyed: `record_hash`
derived from the sha256 alone, not from a path.

Other builders may also adopt deduplication where it applies. For
example, a permission declared multiple times in the manifest can
collapse to one record whose `source` list contains one `Source` per
declaration site, each with its own xpath. No additional schema
changes are needed — `list[Source]` already supports per-location
xpath, line ranges, and DEX IDs.

### Removal of `app_metadata.app_context`

The deprecated `AppContext` model and its `category`,
`category_source`, `interpretation_notes` fields are removed entirely.
All app-context reasoning has lived in `app_capabilities.json` since
v1.2.1; v1.3 deletes the deprecated field rather than carrying it
indefinitely.

### Migration story

v1.3 is a breaking change. Every existing builder needs a
mechanical update: `source=Source(...)` becomes `source=[Source(...)]`.
Every consumer that reads `record.source.path` becomes
`record.source[0].path` for the common single-location case, or
iterates over `record.source` for multi-location records.

Existing v1.2.x evidence files will not load under v1.3 schemas
without conversion. Two migration paths:

- **Re-extract.** Recommended. The pipeline is deterministic and
  re-extracting against a known APK is fast for everything except
  Layer 2 (which dominates regardless).
- **One-time forward migration.** A `v12_to_v13.py` helper that
  wraps every existing `source: Source` as `source: [Source]`,
  removes `app_context` from `app_metadata.json` records, and
  collapses content-identical native binary records (taking the
  union of their per-record `Source` objects). Useful when the
  original APK is no longer available or when re-running Layer 2
  is too expensive.

The schema version constant moves from `"1.2.2"` to `"1.3"`. Layer 4
loaders should reject anything older than `"1.3"` once the migration
is complete.

### What's not in v1.3

These items remain in the v2-deferred section above and are explicitly
not in scope for v1.3:

- Reachability analysis / call graph
- Interprocedural taint analysis
- Native code decompilation (Ghidra-tier)
- `auth_decisions.json`
- CVE database lookups
- Prompt-time serialization formats

v1.3 is a focused cleanup release: schema honesty around multi-source
records, removal of deprecated fields, and the deduplication that
naturally follows. Larger architectural changes wait for v2.
