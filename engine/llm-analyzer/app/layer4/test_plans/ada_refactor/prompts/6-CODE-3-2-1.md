title          Content providers mitigate injection flaws (query hardening) (static)

What this test looks for
Exposed content providers must be hardened against injection (SQL injection in particular): the query path uses parameterized queries / safe query building rather than concatenating caller-supplied input. This is a static, inventory-style evaluation over each EXPOSED provider's query code. Verdict: `pass` (exposed providers are injection-hardened - parameterized/validated), `fail` (an exposed provider is injectable - caller input reaches SQL by concatenation), `n/a` (the app exposes no content providers), or `inconclusive`.

This test is about INJECTION HARDENING. The minimal-exposure / least-privilege judgment (is the provider exported unnecessarily, is it permission-protected) is a SEPARATE test - here, exposure is only the SCOPE GATE: a provider must be exposed for its query path to be externally attacker-reachable. An exported-but-unprotected provider is NOT a finding here on exposure grounds alone; it becomes a finding only if its query body is injectable.

EVIDENCE DISCIPLINE (applies to every row and the verdict)
1. **Every verdict-affecting disposition quotes the code it rests on** - Finding, Compliant, dismissal alike. You may NOT conclude a provider is SQLi-clean (or injectable) without quoting the relevant lines of its `query`/`insert`/`update`/`delete`/`openFile`/`call`/`bulkInsert` body showing how `selection`/`projection`/`sortOrder`/URI segments are handled. "Uses parameterized queries" / "safe from SQLi" without the quoted call is an assertion -> `unverified`.
2. **Read from the code, not the index.** An evidence index (`components.json`, etc.) locates candidates; cite `jadx/sources/...:<line-range>` of the actual provider class body, not the index record or line 1.
3. **No finding by inference/hedge/hypothetical.** A SQLi finding requires quoting the tainted chain: where caller input enters (`selection`/`selectionArgs`/`projection`/`sortOrder`/the URI/`getPathSegments`/`getLastPathSegment`) and where it is concatenated into a SQL/where/table string reaching `rawQuery`/`execSQL`/`query`. "likely concatenates", "may be injectable", "if the selection were attacker-controlled" are NOT evidence -> `unverified`. A parameterized/validated body is Compliant, not a hypothetical finding.
4. **Unresolved determinacy is `unverified`, not a hedge.** If the query is built in a helper you cannot trace within budget, or the routing is obfuscated, the row is `unverified` (deepest unresolved point named). `false_positive_risks` is out-of-APK only; in-APK facts you did not resolve go in `unverified` rows.

Scope gate - which providers are in scope
In scope: EXPOSED (exported) providers, because only then is the query path reachable by other apps with attacker-controlled input. Determine exposure from the manifest: `android:exported="true"`, or the per-type default (providers default exported=true on `targetSdk <= 16`, exported=false on `targetSdk >= 17`). A non-exported provider is out of scope (its query path is not externally attacker-controlled) - note it in one line, do not flag its query. (Exposure itself is judged by the separate minimal-exposure test.)

The good pattern (do not flag)
- Parameterized queries: `SQLiteDatabase.query(table, projection, selection, selectionArgs, ...)` with `?` placeholders bound via `selectionArgs`; `rawQuery(sql, selectionArgs)` with `?` placeholders; `SQLiteStatement` with bound args. -> Compliant; quote it.
- `SQLiteQueryBuilder` with `setStrict(true)` and/or a `setProjectionMap` constraining columns. -> Compliant.
- URI path/segments validated against an allowlist / `UriMatcher` before being used as a table/column name. -> Compliant.
- Library providers configured per their design (`androidx.core.content.FileProvider` and subclasses, `androidx.startup.InitializationProvider`, WorkManager/Firebase init providers) - these do not run app SQL on caller input -> Compliant.

Injection failure modes (on an EXPOSED provider)
- SQLi1 - Concatenated selection/where: `rawQuery`/`execSQL`/`query` where the caller-supplied `selection` (or `sortOrder`) is concatenated into the SQL/where string instead of bound via `selectionArgs`.
- SQLi2 - Unconstrained query builder: `SQLiteQueryBuilder` used WITHOUT `setStrict(true)` and WITHOUT a `setProjectionMap`, passing the caller's `selection`/`projection` straight through (allows arbitrary columns / boolean-logic injection).
- SQLi3 - URI segment as identifier: a URI path/last segment used directly as a table or column name (or interpolated into SQL) without an allowlist / `UriMatcher` validation.

Procedure
1. Read `AndroidManifest.xml` `targetSdkVersion` and every `<provider>` with its `exported` (apply the provider default: exported=true on targetSdk<=16, false on >=17) and intent-filters. Keep the EXPOSED providers; if there are no `<provider>` declarations at all, the verdict is `n/a`. (Non-exported providers: one summary line, out of scope.)
2. For each EXPOSED provider, classify owner (proprietary vs library; prefix is a hint; OEM/ROM vendor prefixes may be first-party; obfuscated/undecidable -> proprietary). Recognized library providers per design are Compliant.
3. **Read the query body of EVERY exposed proprietary provider** - `query`, `insert`, `update`, `delete`, `openFile`, `call`, `bulkInsert`, and any helper query-builder / `getTable` / URI-routing methods (follow helpers once). For each, determine whether caller input reaches SQL by concatenation (SQLi1-3) or is parameterized/validated, and QUOTE the relevant lines. You may not analyze one provider and assert the rest are safe; an exposed provider whose query body you did not read is `unverified` on the injection pillar (not silently Compliant).
4. Conclude per exposed provider: Finding (SQLi1-SQLi3 with the query body quoted); Compliant (parameterized/strict/validated - quoted, or a library provider that runs no caller-driven SQL); Unverified (query body unread, routing obfuscated, owner unresolved); documented candidate (hardening claimed only by an out-of-APK design doc).
5. Budget ~2-4 reads per exposed provider (manifest entry, query bodies, helper) plus 1-2 call-graph hops. If the export state, a query body, or the owner can't be resolved within budget, mark it `unverified` naming the deepest unresolved point (`<ClassFQN>.<method>:<line>`).

Out-of-scope / static limits
Provider logic fully inside native code or a no-source SDK can't be classified statically -> `unverified` (name the entry point). The "design document demonstrates hardening" criterion is partly an out-of-APK artifact; visible in-code parameterization is judged directly, and a hardening claim with no readable code is a documented candidate. The static verdict is made on what was determinable.

Rules
- The verdict is fully static and final. `needs_dynamic_testing` is a non-binding flag (typically false); set true only where the query is runtime-built (recorded `unverified`). It does not change `pass`/`fail`.
- `fail`: >=1 EXPOSED provider with (a) an L2 row showing exposure (manifest, correct provider default applied) AND (b) an L2 row with the query BODY quoted showing caller input concatenated into SQL (SQLi1-SQLi3). A SQLi finding stated with "likely"/"may"/"if the selection were attacker-controlled" instead of the quoted concatenation is INVALID -> `unverified`.
- **Exposure is the scope gate, not a finding here.** An exported-but-unprotected provider is NOT a finding on exposure grounds in this test (that is the minimal-exposure test). Only an injectable query body on an exposed provider is a finding. A non-exported provider is out of scope.
- **Read the query body before flagging; quote it. Do not flag library providers.** A provider is a finding only if a body you read concatenates caller input; parameterized/strict/validated bodies are Compliant. Every exposed provider needs its own quoted SQLi disposition; an unread body is `unverified`, not silently Compliant.
- **targetSdk provider default.** Apply exported=true on targetSdk<=16, exported=false on >=17 when `exported` is unset.
- **No sampling / ownership default (OEM-aware) / false_positive hygiene** as in the suite: every Finding broken out individually (finding count = finding rows); undecidable/obfuscated owner -> proprietary; `false_positive_risks` is out-of-APK only (a design-documented hardening process, runtime-built queries) - in-APK facts (is the selection concatenated? is the provider exported?) resolved by reading code/manifest, unresolved -> `unverified`. Reject "might be parameterized at runtime", "the input might be validated elsewhere".
- `pass`: providers exist and every EXPOSED provider is injection-hardened (parameterized/strict/validated, or a library provider running no caller-driven SQL), with L2 coverage and targetSdk recorded.
- `n/a`: no `<provider>` is declared (manifest read; state this).
- Documented exception: a design-documented hardening process not visible in code is an out-of-APK fact - record a borderline provider as a "documented candidate" with a matching `false_positive_risks` entry; readable in-code parameterization is judged directly.
- `unverified` rows name the deepest unresolved point (or native/SDK entry point). Neither pass nor fail.
- `inconclusive` if rationale counts don't reconcile with L1 rows (finding count = finding rows), if any false_positive_risk references in-APK code, if a finding was dropped/out-of-scoped without evidence, or if any `fail` lacks its exposure + quoted-body L2 rows.

Self-check before emitting (per finding)
For every Finding confirm: (1) the provider is exposed (manifest, targetSdk default applied) - the scope gate; (2) you READ and quoted the query body showing caller input concatenated into SQL (not the method's existence, not a hypothetical); (3) owner decided from evidence (OEM-aware; obfuscated -> proprietary), not a library provider.
Hedge/hypothetical scan: "likely", "may", "appears", "if ... were", "could", "might" in a finding's evidence -> downgrade to `unverified`.
Evidence-discipline gate (all rows): every Compliant/SQLi-clean row quotes the actual query body (not the index or a bare line range); every exposed provider has its own quoted disposition; an unread body is `unverified`.
Before any `pass`/`fail`: confirm no exposed provider was concluded clean without a quoted query body, no non-exported provider was flagged, and no `false_positive_risks` entry describes an unresolved in-APK fact. Confirm counts reconcile (no sampling). Only then emit.
