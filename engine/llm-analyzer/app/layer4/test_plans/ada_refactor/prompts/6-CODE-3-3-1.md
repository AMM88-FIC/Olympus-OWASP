title          No arbitrary-URL redirection / untrusted loads in WebViews (scheme+host allowlist, SafeBrowsing) (static)

What this test looks for
WebViews must not load arbitrary or untrusted URLs: every loaded resource is developer-controlled, the scheme AND host of loaded URIs are validated against an allowlist, and SafeBrowsing is enabled. This is a static, inventory-style evaluation over each WebView's load calls and navigation handling. Verdict: `pass` (no WebViews; OR only trusted content loaded, with scheme/host allowlist validation and SafeBrowsing enabled), `fail` (some WebView can load arbitrary/untrusted URLs), `n/a` (the app has no WebViews - passes automatically), or `inconclusive`.

RELATIONSHIP TO THE OTHER WEBVIEW TESTS (do not conflate): the WebView-safe-JavaScript test gates on JavaScript being enabled and judges content-source trust only then; the protocol-handlers test judges file-access settings. THIS test is about ARBITRARY-URL REDIRECTION and untrusted loads - it applies REGARDLESS of JS state (an attacker-definable URL is a problem - open redirect, phishing, local-file/credential exposure - even with JS disabled) - plus scheme/host allowlist validation and SafeBrowsing. There is NO JS short-circuit here.

EVIDENCE DISCIPLINE (applies to every row and the verdict)
1. **Every verdict-affecting disposition quotes the code it rests on** - Finding, Compliant, dismissal alike. Quote the `loadUrl`/`loadData`/`loadDataWithBaseURL`/`postUrl` call plus the construction of the URL argument, the navigation handler (`shouldOverrideUrlLoading`/`shouldInterceptRequest`), and any allowlist/`setSafeBrowsingEnabled` call. A disposition with no quoted code is an assertion -> `unverified`.
2. **Read from the code, not the index.** An evidence index locates candidates; cite `jadx/sources/...:<line-range>` of the actual load/handler code, not the index record or line 1.
3. **No finding by inference/hedge/hypothetical.** A fail requires quoting (a) the load/navigation site, AND (b) the URL source shown to be user-definable/untrusted (traced to user input, an Intent/deep-link param, a server-supplied URL, or no scheme/host allowlist) OR an explicit `setSafeBrowsingEnabled(false)`. "likely loads untrusted URLs", "may redirect", "if the URL were attacker-controlled" are NOT evidence -> `unverified`. A load of a developer-constant/allowlisted URL is Compliant, not a hypothetical finding.
4. **Unresolved determinacy is `unverified`, not a hedge.** If the URL is built in a helper you cannot trace, or host trust cannot be determined, the row is `unverified` (deepest unresolved point named). `false_positive_risks` is out-of-APK only; in-APK facts you did not resolve go in `unverified` rows.

What makes a WebView load UNSAFE
Source (untrusted/user-definable): a URL/content from `getIntent().getData()`/`getQueryParameter`/extras (deep link), user-entered text, a file path/`content://` the user controls, or a server response carrying an attacker-influenceable URL. Failure modes:
- AR1 - Arbitrary/user-definable URL: the URL passed to `loadUrl`/`postUrl`/`loadDataWithBaseURL` is derived from user input / an Intent/deep-link param, so the user or another app defines what loads (open redirect).
- AR2 - No scheme/host allowlist: a non-constant URL is loaded without validating BOTH its scheme (https) AND its host against an allowlist - the navigation can be redirected to an untrusted origin (incl. a `shouldOverrideUrlLoading` that returns false / lets all navigations proceed, or follows server-supplied redirects without re-checking the host).
- AR3 - Untrusted/non-HTTPS origin: loads `http://` or a third-party host not controlled by the developer.
- AR4 - SafeBrowsing explicitly disabled: `settings.setSafeBrowsingEnabled(false)` (or `android:value="false"` for the `android.webkit.WebView.EnableSafeBrowsing` manifest meta-data).

API defaults (do not flag a safe default's absence)
- `setSafeBrowsingEnabled` defaults to TRUE for the system WebView on API >= 26. So ABSENCE of the call is Compliant on modern targets; a finding (AR4) requires an explicit `setSafeBrowsingEnabled(false)` or the manifest meta-data set to false - quoted. Do NOT flag the mere absence of a setSafeBrowsingEnabled call.

The good pattern (do not flag)
- A WebView that only loads a developer-constant HTTPS URL to a first-party host, or local content (`file:///android_asset/...`, bundled `loadData` HTML) -> trusted load, Compliant. Quote the constant/local source.
- A navigation handler that validates scheme==https AND host against an allowlist (or `UriMatcher`/explicit host check) before proceeding, and cancels/blocks others -> Compliant. Quote the check.
- SafeBrowsing enabled (explicit `setSafeBrowsingEnabled(true)`), or simply not disabled on API>=26 -> Compliant.
- Library/SDK WebViews (ad/IAP/login SDK's own WebView) configured by the library -> the library's; focus on proprietary WebViews the app configures + loads.

Procedure
1. Determine WebView presence: `grep -rEn "new WebView|WebView\(|loadUrl|postUrl|loadData|loadDataWithBaseURL|WebViewClient|shouldOverrideUrlLoading|shouldInterceptRequest|setSafeBrowsingEnabled" jadx/sources/` and check the manifest for WebView usage. If there are no WebViews, the verdict is `n/a` (passes automatically).
2. Per WebView, read every load call (`loadUrl`/`postUrl`/`loadData`/`loadDataWithBaseURL`) and trace the URL/content argument to its origin: developer constant/local (trusted) vs user/Intent/server/untrusted (AR1/AR3). Quote the load and the source construction.
3. Read the navigation handling (`shouldOverrideUrlLoading`, `shouldInterceptRequest`): is there a scheme(==https)+host(allowlist) check before a navigation proceeds, and are others blocked? Absent/permissive -> AR2. Quote the handler.
4. Check SafeBrowsing: an explicit `setSafeBrowsingEnabled(false)` or manifest meta-data false -> AR4. Absence on API>=26 -> Compliant (default true). Quote any explicit setting.
5. Classify owner (proprietary vs library; prefix is a hint; OEM/ROM vendor prefixes may be first-party; obfuscated/undecidable -> proprietary).
6. Conclude per WebView: Compliant (trusted constant/local load + scheme/host allowlist where dynamic + SafeBrowsing not disabled - quoted); Finding (AR1-AR4 - quoted); Unverified (load source untraceable, host trust indeterminate, owner unresolved); documented candidate (host trust justified only out-of-APK).
7. Budget ~2-4 reads per WebView (each load, the navigation handler, the SafeBrowsing setting) plus 1-2 call-graph hops. If the load source, handler, or owner can't be resolved within budget, mark it `unverified` naming the deepest unresolved point (`<ClassFQN>.<method>:<line>`).

Out-of-scope / static limits
WebView content built/loaded in native code or a no-source SDK -> `unverified` (name the entry point). Whether a remote host is "trusted" can depend on facts outside the APK; a first-party HTTPS constant is trusted, an unknown third-party host loaded without an allowlist is at least `unverified` (or AR2/AR3 if clearly untrusted/cleartext). The static verdict is made on what was determinable.

Rules
- The verdict is fully static and final. `needs_dynamic_testing` is a non-binding flag (typically false); it does not change `pass`/`fail`.
- `fail`: >=1 WebView with an L2 row showing AR1 (user-definable URL, source quoted), AR2 (non-constant load with no scheme+host allowlist, handler quoted), AR3 (untrusted/non-HTTPS origin), or AR4 (explicit `setSafeBrowsingEnabled(false)` / manifest meta-data false), plus owner. A finding stated with "likely"/"may"/"if the URL were attacker-controlled" instead of the quoted unsafe load/handler is INVALID -> `unverified`.
- **No JS short-circuit.** Analyze the load source and redirect handling regardless of JS state; an arbitrary/untrusted load is a finding even with JS disabled.
- **Read before flagging; quote it. Do not flag trusted loads or library WebViews, and do not flag a safe default's absence.** A constant first-party HTTPS / local load with a host allowlist is Compliant. Absence of `setSafeBrowsingEnabled` is Compliant on API>=26 (default true) - only an explicit disable is AR4.
- **No sampling / ownership default (OEM-aware) / false_positive hygiene** as in the suite: every Finding broken out individually (finding count = finding rows); undecidable/obfuscated owner -> proprietary; `false_positive_risks` out-of-APK only (host trust established outside the APK, URLs delivered at runtime by first-party server) - in-APK facts (where does the URL come from? is there an allowlist? is SafeBrowsing disabled?) resolved by reading, unresolved -> `unverified`. Reject "might load only trusted content", "the host may be trusted", "might validate elsewhere".
- `pass`: no WebViews, OR every WebView loads only trusted content (constant first-party HTTPS / local) with scheme+host allowlist validation for any dynamic load and SafeBrowsing not disabled, with L2 coverage.
- `n/a`: the app has no WebViews (enumeration performed; passes automatically; state this).
- `unverified` rows name the deepest unresolved point (or native/SDK entry point). Neither pass nor fail.
- `inconclusive` if rationale counts don't reconcile with L1 rows (finding count = finding rows), if any false_positive_risk references in-APK code, if a finding was dropped without evidence, if a finding was inferred from a safe-default absence (SafeBrowsing), or if any `fail` lacks its quoted load/handler L2 rows.

Self-check before emitting (per finding)
For every Finding confirm: (1) the load call or navigation handler is quoted AND the URL source is traced/quoted as user-definable/untrusted (not a developer constant, not a hypothetical) OR an explicit SafeBrowsing-disable is quoted; (2) for AR2, the absence of a scheme+host allowlist is shown in the quoted handler (not assumed); (3) owner decided from evidence (OEM-aware; obfuscated -> proprietary), not a library WebView.
Defaults check: confirm you did not flag the mere absence of `setSafeBrowsingEnabled` on API>=26 (safe default true).
Hedge/hypothetical scan: "likely", "may", "appears", "if ... were", "could", "might" in a finding's evidence -> downgrade to `unverified`.
Before any `pass`/`fail`: confirm every WebView's load source and navigation handling were read and quoted (unread -> `unverified`), no safe-default absence was flagged, and no `false_positive_risks` entry describes an unresolved in-APK fact. Confirm counts reconcile (no sampling). Only then emit.
