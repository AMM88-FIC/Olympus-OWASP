title          Implicit intent use is appropriate and returned data is handled safely (static)

What this test looks for
Implicit intents (launched without an explicit component, so any app can receive them) must be appropriate for the functionality, must not leak sensitive data to whichever app the OS resolves them to, and any data returned by another app must be handled safely (the result in `onActivityResult` is untrusted input). This is a static, inventory-style evaluation over outbound implicit intents and their result handlers. Verdict: `pass` (no implicit intents; OR they are appropriate, leak no sensitive data, and returns are handled safely), `fail` (an implicit intent is inappropriate, leaks sensitive data, or its return is handled unsafely), `n/a` (the app uses no implicit intents), or `inconclusive`.

This is the OUTBOUND counterpart to the exposed-IPC test (which covers what the app EXPOSES to others). Here the concern is what the app SENDS OUT and what it does with what comes BACK.

EVIDENCE DISCIPLINE (applies to every row and the verdict)
1. **Every verdict-affecting disposition quotes the code it rests on** - Finding, Compliant, dismissal alike. Quote the intent construction (action, and absence of `setClassName`/`setComponent`/`setPackage`), the extras/data put into it, the dispatch call (`startActivity`/`startActivityForResult`/`sendBroadcast`), and - for returns - the `onActivityResult` body. A disposition with no quoted code is an assertion -> `unverified`.
2. **Read from the code, not the index.** An evidence index (`outgoing_intents.json`, etc.) locates candidates; cite `jadx/sources/...:<line-range>` of the actual construction/dispatch/handler, not the index record or line 1.
3. **No finding by inference/hedge/hypothetical.** A leak finding requires quoting the sensitive value being put into the implicit intent and the dispatch; an unsafe-return finding requires quoting where the returned data is read in `onActivityResult` and the sink it flows to without validation. "likely leaks", "may be sensitive", "if the returned data were attacker-controlled" are NOT evidence -> `unverified`. An appropriate implicit intent with non-sensitive data and a validated/absent return is Compliant, not a hypothetical finding.
4. **Unresolved determinacy is `unverified`, not a hedge.** If the extra's content or the returned-data flow can't be traced within budget, the row is `unverified` (deepest unresolved point named). `false_positive_risks` is out-of-APK only; in-APK facts you did not resolve go in `unverified` rows.

What is an IMPLICIT intent (scope)
An `Intent` dispatched WITHOUT an explicit target: constructed with an action (`new Intent(Intent.ACTION_SEND)`, `new Intent(action, uri)`) and NOT given `setClassName`/`setComponent`/`setClass`/an explicit `setPackage` to a specific app, then passed to `startActivity`/`startActivityForResult`/`startActivity(createChooser(...))`/`sendBroadcast`/`sendOrderedBroadcast`/`bindService`. An intent with an explicit component or a specific `setPackage` is NOT implicit (out of scope). If there are no implicit intents, the verdict is `n/a`.

The good pattern (do not flag)
- **Implicit is NOT a finding by itself.** Most cross-app actions are appropriately implicit: `ACTION_VIEW` a public URL, `ACTION_SEND`/`createChooser` to share non-sensitive content, `ACTION_PICK`/`ACTION_GET_CONTENT`/`ACTION_IMAGE_CAPTURE`, dialer/maps/store intents. An implicit intent carrying only non-sensitive data and not mishandling its return is Compliant.
- Sending data that is appropriate to the action (e.g. a user-chosen document to a share target) is fine; the leak finding is for SENSITIVE data (credentials, tokens, keys, PII, internal file contents) placed where an arbitrary resolver can read it.
- `onActivityResult` that validates returned data before use (checks `resultCode==RESULT_OK`, verifies/sanitizes a returned URI's scheme/authority, range/format-checks values, takes persistable URI permission deliberately) -> Compliant; quote the validation.
- Using an explicit chooser does not make a sensitive-data leak safe (the user may still pick an attacker app) - judge by the data sensitivity.

Failure modes
- II1 - Inappropriate implicit intent: an action that should target a specific trusted component is sent implicitly where any app can intercept it (e.g. an internal/auth/IPC action broadcast implicitly), exposing the operation to arbitrary apps.
- II2 - Sensitive-data leak via implicit intent: a sensitive value (token, credential, key, PII, internal file content) is placed in the extras/data/clip of an implicit intent (incl. an implicit `sendBroadcast` without a receiver permission), so the resolving app receives it.
- RD1 - Unsafe return handling: `onActivityResult` (or an ActivityResult callback) consumes data returned by another app and uses it without validation - e.g. loads a returned URI into a WebView, opens/reads a returned `content://`/file path without checking authority, passes a returned value to a SQL/file/intent sink, or trusts it without `resultCode`/content checks.

Procedure
1. Enumerate implicit-intent dispatch sites: `grep -rEn "new Intent\(|setAction|startActivity|startActivityForResult|createChooser|sendBroadcast|sendOrderedBroadcast|registerForActivityResult|onActivityResult" jadx/sources/`. For each `Intent`, determine whether it is implicit (action set, no explicit component/package). Discard explicit intents (out of scope). If none are implicit, the verdict is `n/a`.
2. For each implicit intent, read the extras/data/clip put into it and trace whether any sensitive value flows in (II2); judge whether the action is appropriate to be implicit (II1). QUOTE the construction, the extra, and the dispatch.
3. For each `startActivityForResult`/`registerForActivityResult`, read the corresponding `onActivityResult`/callback body and trace the returned data to its use - is it validated before reaching a sink (Compliant) or used raw (RD1)? QUOTE the handler and the sink.
4. Classify owner (proprietary vs library; prefix is a hint; OEM/ROM vendor prefixes may be first-party; obfuscated/undecidable -> proprietary). Library-internal implicit intents configured by the library are the library's; focus on proprietary dispatch/handlers.
5. Conclude per site: Finding (II1/II2/RD1 with the relevant code quoted); Compliant (appropriate implicit intent, no sensitive data, return validated/absent - quoted); Unverified (extra content or return flow unresolved, owner unresolved); documented candidate (appropriateness justified only by an out-of-APK design doc).
6. Budget ~2-4 reads per site (construction, extras, dispatch, result handler) plus 1-2 call-graph hops to trace a sensitive source or a returned value. If the data content or the return flow can't be resolved within budget, mark it `unverified` naming the deepest unresolved point (`<ClassFQN>.<method>:<line>`).

Out-of-scope / static limits
Intent dispatch/handling inside native code or a no-source SDK -> `unverified` (name the entry point). Whether a piece of data is "sensitive" is read from context (variable/field names, source API); genuinely indeterminate sensitivity -> `unverified`. The static verdict is made on what was determinable.

Rules
- The verdict is fully static and final. `needs_dynamic_testing` is a non-binding flag (typically false); it does not change `pass`/`fail`.
- `fail`: >=1 implicit intent with an L2 row showing II1 (inappropriate implicit action, context quoted), II2 (sensitive value quoted being placed in the implicit intent + dispatch), or RD1 (the `onActivityResult`/callback body quoted showing returned data used without validation), plus the implicit-construction evidence and owner. A finding stated with "likely"/"may"/"if the data were sensitive" instead of the quoted leak/return path is INVALID -> `unverified`.
- **Implicit is not a finding by itself.** An appropriate implicit action (VIEW/SEND/PICK/etc.) carrying non-sensitive data with a safe/absent return is Compliant. The finding is sensitive-data-in-implicit-intent, an inappropriate implicit action, or unsafe return handling - each quoted.
- **Read before flagging; quote it. Do not flag explicit intents or library-internal intents.** An intent with an explicit component/specific package is out of scope. Resolve the extra's content and the return flow; do not guess sensitivity.
- **No sampling / ownership default (OEM-aware) / false_positive hygiene** as in the suite: every Finding broken out individually (finding count = finding rows); undecidable/obfuscated owner -> proprietary; `false_positive_risks` out-of-APK only (a design-documented justification that an action must be implicit, data sensitivity established outside the APK) - in-APK facts (is the extra sensitive? is the intent implicit? is the return validated?) resolved by reading, unresolved -> `unverified`. Reject "the data might not be sensitive", "the returned URI might be validated elsewhere", "might be a deliberate choice".
- `pass`: no implicit intents, OR every implicit intent is appropriate, carries no sensitive data, and handles any return safely (validated), with L2 coverage.
- `n/a`: the app uses no implicit intents (enumeration performed; state this).
- `unverified` rows name the deepest unresolved point (or native/SDK entry point). Neither pass nor fail.
- `inconclusive` if rationale counts don't reconcile with L1 rows (finding count = finding rows), if any false_positive_risk references in-APK code, if a finding was dropped/out-of-scoped without evidence, or if any `fail` lacks its implicit-construction + (II2/RD1) quoted-body L2 rows.

Self-check before emitting (per finding)
For every Finding confirm: (1) the intent is implicit - construction quoted showing an action and NO explicit component/package; (2) the issue is quoted - the sensitive extra + dispatch (II2), the inappropriate-action context (II1), or the `onActivityResult` body showing returned data used without validation (RD1) - not a hypothetical; (3) owner decided from evidence (OEM-aware; obfuscated -> proprietary), not a library intent.
Hedge/hypothetical scan: "likely", "may", "appears", "if ... were", "could", "might" in a finding's evidence -> downgrade to `unverified`.
Before any `pass`/`fail`: confirm every implicit intent's data content and every result handler were read and quoted (unread -> `unverified`), no explicit intent was flagged, no implicit intent was flagged merely for being implicit, and no `false_positive_risks` entry describes an unresolved in-APK fact.
