What this test looks for
The app must not bundle a third-party library at a version affected by a known CVE of severity CVSS >= 7.0 - unless there is a valid justification (the vulnerable code path is not invoked, or no patch exists yet AND the vendor has a regular patching process). This is a static, inventory-style evaluation: build the exact dependency inventory from the artifact, map each (library, version) to known CVEs via an authoritative vulnerability source, and apply the justification logic. Verdict: `pass` (no third-party lib with a CVSS >= 7.0 CVE, or all such are validly justified), `fail` (a third-party lib at a version with a CVSS >= 7.0 CVE and no acceptable justification), `n/a` (the app uses no third-party libraries), or `inconclusive`.

CRITICAL - CVE DATA MUST COME FROM AN AUTHORITATIVE SOURCE, NEVER FROM MEMORY
You do NOT know from training which versions are affected by which CVEs, and CVE/CVSS data changes constantly. You MUST obtain every CVE and its CVSS score from an authoritative vulnerability source - a vulnerability-lookup tool if one is available to you (e.g. OSV, GitHub Security Advisory, NVD), or a CVE feed provided to you for this run. NEVER assert, recall, infer, or estimate a CVE id, a CVSS score, or an "affected version range" from your own knowledge. If you cannot consult an authoritative source for a given component, that component is `unverified` (CVE status undetermined), NOT a pass and NOT a guessed finding. A finding MUST cite the concrete CVE id, the CVSS score (>= 7.0), the affected-version range, and the source it came from.

EVIDENCE DISCIPLINE (applies to every row)
1. **Every verdict-affecting disposition quotes its evidence** - the library coordinate + exact version from the artifact, AND (for a finding) the CVE id/CVSS/affected-range/source from the vulnerability database. A disposition with no quoted version + no cited CVE source is an assertion -> `unverified`.
2. **Read the version from the artifact, not from a guess.** Cite where the version came from (a dependency manifest, a bundled `.version`/`pom.properties`, a class/string constant, the lib's known version marker). If you can identify the library but not pin its exact version, it is `unverified` for CVE matching (a CVE verdict requires the exact version).
3. **No finding by inference/hedge.** "probably vulnerable", "this version may have CVEs", "old version, likely affected" are NOT evidence -> `unverified`. A finding requires the concrete CVE + CVSS >= 7.0 + affected range from the source, and the bundled version shown to fall in that range.
4. **Unresolved determinacy is `unverified`, not a hedge.** Unknown exact version, no source consulted, or an ambiguous coordinate -> `unverified` (deepest unresolved point named: the library whose version/CVE status could not be pinned). `false_positive_risks` is for out-of-artifact factors only.

Scope - what is a "third-party library"
Bundled external dependencies: AndroidX/Jetpack, Google Play Services/Firebase, OkHttp/Retrofit/Gson/Glide/Picasso/Bouncy Castle, SDKs (analytics, ads, auth, payments), and any packaged class tree that is not the app's own first-party code. The app's own (proprietary, including OEM/ROM first-party) code is NOT a third-party library for this test - homemade-vuln issues belong to the crypto/code tests. Use ownership reasoning (prefix is a hint; OEM/ROM vendor prefixes may be first-party; obfuscated/undecidable owner is treated as first-party-proprietary here, i.e. not a third-party-CVE candidate, unless a recognizable library fingerprint is present).

Building the inventory (version pinning)
Identify each bundled library and its EXACT version from, in order of reliability: a dependency lockfile/manifest if present in the evidence (e.g. a bundled BOM, `dependencies` metadata), embedded version markers (`META-INF/.../pom.properties`, `*.version` files, `BuildConfig`/`VERSION_NAME` constants in the lib's package, resource version strings), or a reliable class-set/byte fingerprint mapped to a version. Record the coordinate (group:artifact) and version. A library whose presence is clear but whose exact version cannot be pinned is `unverified` (CVE matching needs the exact version).

Justification logic (a CVSS >= 7.0 CVE is NOT automatically a fail)
For each library at a version with a CVSS >= 7.0 CVE (per the source), determine the disposition:
- Finding: the vulnerable code path is reachable/used by the app, OR reachability cannot be excluded, AND no acceptable justification applies.
- Justified (Compliant, record the justification): (a) the specific vulnerable API/class/method of the CVE is NOT invoked anywhere by the app or other libraries (demonstrated by reading the call sites / `find_callers` on the vulnerable symbol - cite it); OR (b) no patched version exists yet AND the vendor has a regular patching process (an out-of-artifact fact - documented candidate). Justification (a) is in-artifact and judged directly; (b) is a documented candidate.
- Unverified: the CVE source could not be consulted, the version could not be pinned, or reachability of the vulnerable code could not be resolved within budget.

Procedure
1. Enumerate bundled third-party libraries and pin each exact version from the artifact (sources above). If there are no third-party libraries, the verdict is `n/a`.
2. For EACH (library, version), query the authoritative vulnerability source for CVEs. Record every CVE with CVSS >= 7.0 whose affected range includes the bundled version, with id + score + range + source. (No source available for a component -> `unverified` for that component.)
3. For each CVSS >= 7.0 match, apply the justification logic: determine whether the CVE's specific vulnerable symbol is invoked (read call sites / `find_callers` on the vulnerable class/method named in the advisory) - if provably never invoked, Justified(a); else Finding (or `unverified` if reachability is unresolved). The no-patch-yet + vendor-process case is a documented candidate.
4. Conclude per library: Finding (CVSS >= 7.0 CVE, version in range, vulnerable code reachable/not-excluded, unjustified - with CVE+score+range+source and version cited); Compliant (no CVSS >= 7.0 CVE for the pinned version, OR justified(a) with the non-invocation shown); Unverified (version unpinned, no source consulted, or reachability unresolved); documented candidate (no-patch-yet + vendor process, an out-of-artifact justification).
5. Budget: pin version + one source query per library; for a CVSS >= 7.0 hit, ~1-3 reads / `find_callers` hops to test invocation of the vulnerable symbol. If unresolved, `unverified` naming the library and the unresolved point.

Out-of-scope / static limits
The CVE/CVSS facts are inherently external (a live vulnerability database); this test depends on that source and on the version being pinnable from the artifact. Where either is unavailable, the affected components are `unverified` and `needs_dynamic_testing`/external-lookup may be flagged. The app's first-party code is out of scope (other tests cover it). The static verdict is made on what was determinable from the artifact + the cited source.

Rules
- The verdict is fully static and final given the cited vulnerability source. `needs_dynamic_testing`/external-lookup is a non-binding flag for components that could not be pinned or sourced. It does not change `pass`/`fail`.
- **CVE facts only from an authoritative source, never from memory.** Every finding cites CVE id + CVSS >= 7.0 + affected range + source, and shows the pinned version in range. A "finding" without a cited CVE/source, or based on recalled/estimated vulnerability knowledge, is INVALID -> `unverified`. No source consultable for a component -> `unverified`, never a guessed pass or fail.
- `fail`: >=1 third-party library with (a) an L2 row pinning the exact version from the artifact, (b) an L2 row citing a CVSS >= 7.0 CVE (id/score/range/source) covering that version, AND (c) the vulnerable code reachable or not-excludable (no valid justification). 
- **CVSS >= 7.0 is not automatically a fail.** If the CVE's specific vulnerable symbol is provably never invoked (shown via call-site read / `find_callers`), it is Justified(a) -> Compliant (record it). No-patch-yet + vendor regular-patching process is a documented candidate (out-of-artifact).
- **Exact version required.** A library you cannot pin to an exact version is `unverified` (CVE matching needs the precise version) - do not fail or pass it on a guessed version.
- **No sampling / ownership (first-party out of scope) / false_positive hygiene** as in the suite: every Finding broken out individually (finding count = finding rows); first-party/OEM code is out of scope (not a third-party lib); `false_positive_risks` is out-of-artifact only (no patch available yet, vendor patching cadence, a CVE disputed/withdrawn at the source) - in-artifact facts (which version? is the symbol invoked?) resolved by reading, unresolved -> `unverified`. Reject "the CVE might not apply", "the library might be patched".
- `pass`: third-party libs exist and none at its pinned version has a CVSS >= 7.0 CVE per the cited source, or all such are justified(a)/documented, with L2 coverage naming the source.
- `n/a`: no third-party libraries (enumeration performed; state this).
- `unverified` rows name the library and the unresolved point (unpinned version / no source / reachability). Neither pass nor fail.
- `inconclusive` if rationale counts don't reconcile with L1 rows (finding count = finding rows), if any finding lacks a cited CVE/source, if any CVE was asserted from memory, if a finding was dropped without evidence, or if any `fail` lacks its version + CVE-source + reachability L2 rows.
