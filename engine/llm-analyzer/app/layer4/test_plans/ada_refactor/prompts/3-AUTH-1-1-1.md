title          PKCE used to protect the authorization-code grant in OAuth 2.0 / OpenID Connect (static)

What this test looks for
If the app performs an OAuth 2.0 / OpenID Connect authorization-code flow itself, that flow must use PKCE (Proof Key for Code Exchange): a per-request `code_verifier` (high-entropy random), a `code_challenge = BASE64URL(SHA-256(code_verifier))`, `code_challenge_method=S256` sent on the authorization request, and the `code_verifier` sent on the token exchange. This is a static evaluation of the app's authorization flows. Verdict: `pass` (every first-party authorization-code flow uses PKCE), `fail` (a first-party code-grant flow runs without PKCE, or PKCE is explicitly disabled), `n/a` (the app uses no OAuth/OIDC, or delegates authentication entirely to a third-party/managed SDK), or `inconclusive`.

Source is ground truth. A network/string evidence index is a candidate list only - confirm the flow, the library configuration, and the PKCE parameters by reading the code in `jadx/sources/`, the manifest (redirect-URI scheme, custom-tab/intent filters), and resources/config. The `find_callers`/`find_callees` call graph gives *candidate* chains, not confirmed flow.

Scope - is there a first-party authorization-code flow?
1. Detect OAuth/OIDC usage at all. Signals: authorization-code parameters `response_type=code`, `grant_type=authorization_code`, `redirect_uri`, `client_id`, `scope`, an `/authorize` + `/token` endpoint pair; Custom Tabs / `CustomTabsIntent` or a WebView opening an authorization URL; OAuth/OIDC libraries (`net.openid.appauth`, Auth0, Okta OIDC, Microsoft MSAL, etc.). If none -> `n/a`.
2. Classify each flow's owner (evidence-based; package prefix is a hint only; in OEM/ROM apps platform-/vendor-looking prefixes may be first-party; an undecidable/obfuscated owner defaults to **proprietary, in scope** - never silently dropped). A flow handled **entirely** by a managed third-party SDK that owns the whole exchange (e.g. Google Sign-In/GMS, Firebase Auth, Facebook Login, a vendor SSO SDK) is delegated -> `n/a` for that flow. A flow the app constructs/handles itself (builds the authorization request, receives the redirect, exchanges the code), including via a thin library like AppAuth that the app configures, is **first-party and in scope**.
3. Only the authorization-**code** grant is in scope for PKCE. If a flow uses the implicit grant (`response_type=token`) or ROPC, note it (implicit is deprecated and is its own concern) but PKCE does not apply; absence of any code grant in an OAuth-using app is reported, not auto-failed under this test.

PKCE detection (per in-scope flow)
- Manual implementation present (PASS signals): the code builds/sends `code_challenge` + `code_challenge_method` on the authorization request AND a `code_verifier` on the token request; a `code_verifier` generated from a CSPRNG (`SecureRandom`) and a `code_challenge` computed as `BASE64URL(SHA-256(verifier))`. `S256` is required-strength; a `plain` challenge method is technically PKCE but weak - treat as pass-with-note, not a clean pass.
- Library defaults (PASS signals): **AppAuth (`net.openid.appauth`) enables PKCE by default** - an `AuthorizationRequest.Builder` used normally generates the verifier/challenge automatically, so PKCE is present unless explicitly disabled. Auth0.Android `WebAuthProvider`, Okta OIDC, and MSAL likewise use PKCE by default for the code flow. Presence of these libraries driving a code flow, without disabling PKCE, is a pass.
- FAIL signals: a first-party code-grant flow with no `code_challenge`/`code_verifier`/`S256` artifacts anywhere on the path AND no PKCE-by-default library driving it; or PKCE explicitly disabled (e.g. AppAuth `setCodeVerifier(null, null, null)`, a config flag turning PKCE off).

Procedure
1. Detect OAuth/OIDC usage (step 1 signals), e.g. `grep -rEn "response_type|grant_type|authorization_code|code_challenge|code_verifier|code_challenge_method|net\.openid\.appauth|CustomTabsIntent|WebAuthProvider|/authorize|/oauth" jadx/sources/` plus a manifest scan for the redirect-URI scheme/intent filter. If nothing -> `n/a`.
2. For each flow, classify owner/scope (step 2). Delegated-to-managed-SDK flows -> `n/a` for that flow with an L2 noting the SDK owns the exchange.
3. For each in-scope first-party code-grant flow, read the authorization-request construction and the token-exchange call and look for the PKCE artifacts / library default behavior. Follow the request builder and any wrapper once.
4. **Ownership + reachability (mandatory for a `fail`).** Confirm proprietary code drives the flow with `find_callers`/reading the source, and cite it. A `fail` asserted without an evidenced proprietary flow and a cited caller/flow path is invalid -> `unverified`.
5. Conclude per flow: Pass (PKCE present / default-on, in proprietary code); Pass-with-note (PKCE present but `plain` method); Fail (in-scope code grant, no PKCE / PKCE disabled, proprietary & reachable); N/A (delegated/no code grant); Unverified (flow assembled from server/runtime config that can't be resolved statically, or owner/path unresolved within budget).
6. Budget ~2-5 reads per flow (authorization request, token exchange, library config, manifest) plus 1-2 call-graph hops. If PKCE presence, the flow type, the owner, or reachability can't be resolved within the bytecode within budget, mark the flow `unverified` naming the deepest unresolved point (`<ClassFQN>.<method>:<line>`).

Out-of-scope / static limits
The authoritative confirmation for PKCE is a network capture of the live authorization/token requests; static analysis infers PKCE from code and library defaults. Where the authorization request is assembled from server-provided or runtime config not present in the bytecode, PKCE presence cannot be confirmed statically -> `unverified`, and `needs_dynamic_testing` may be set as a non-binding flag for a capture. Flows fully inside native code or a no-source SDK -> `unverified` (name the entry point). The static verdict is made on what was determinable.

Rules
- The verdict is fully static and final. `needs_dynamic_testing` is a non-binding flag; set true only to recommend a network capture for a flow whose PKCE state could not be confirmed statically (recorded `unverified`). It does not change `pass`/`fail`.
- `fail`: >=1 first-party authorization-code flow with (a) an L2 row showing it is an authorization-code grant, (b) an L2 row showing PKCE is absent (no code_challenge/verifier/S256 and no PKCE-by-default library driving it) or explicitly disabled, AND (c) an L2 row giving an evidenced proprietary-ownership + reachability determination. A `fail` may not be asserted from a string search alone or from the rationale prose.
- `pass`: every in-scope first-party code-grant flow has evidenced PKCE (manual artifacts, or a PKCE-by-default library not disabled), with L2 coverage. A `plain` challenge method is Pass-with-note (record the weakness), not silently clean.
- `n/a`: no OAuth/OIDC usage at all, OR every flow is delegated to a managed third-party SDK / is not an authorization-code grant. State which, with L2 evidence.
- **Do not fail an AppAuth/Auth0/Okta/MSAL flow merely because the literal string `code_challenge` is absent** - these libraries generate PKCE internally and by default; a fail requires evidence PKCE was disabled.
- Ownership default (OEM-aware): decide owner from evidence, not prefix; undecidable/obfuscated -> proprietary (in scope); never silently out-of-scope a flow.
- `unverified` rows name the deepest unresolved point (or the native/SDK entry point). Such flows are neither pass nor fail.
- `false_positive_risks` is for factors **outside the static artifact only** (PKCE/flow config delivered at runtime by the server, an SDK version whose default differs, network-only confirmation). Statements about what the in-APK code does must be resolved by reading it (Pass/Fail/`unverified`), not placed here.
- `inconclusive` if rationale counts don't reconcile with L1 rows, if any false_positive_risk references in-APK code, or if any `fail` lacks its three L2 rows.

Self-check before emitting (per fail)
For every Fail confirm: (1) the flow is evidenced as a first-party authorization-code grant; (2) PKCE absence/disabling is shown from code, not merely from a missing string, and no PKCE-by-default library is silently driving the flow; (3) an evidenced proprietary-ownership decision was made and the flow/caller path cited. If any is missing, downgrade to `unverified` or re-scope to `n/a`. Then confirm the rationale counts reconcile with the rows and no `false_positive_risks` entry describes in-APK code. Only then emit.
